## 優先修正
### P0：訂單可繞過伺服器驗證
firestore.rules:64–82：create 只驗證 userId，沒有禁止自行寫入 confirmed、payments 或 balanceDue；update 只凍結部分欄位，日期、分店、折扣等仍可改。lockPasscode.ts:135–162 依 confirmed、日期及尚欠判定發碼。若雲端規則與 repo 相同，可偽造符合發碼條件的單。應禁止客戶直接建立敏感訂單資料，全部經驗證 API，並以欄位白名單限制可更新內容。
### P0：套餐價格仍信任客戶輸入
src/app/api/bookings/create/route.ts:140–162、234–246：只要帶 packageSlug 就略過一般重算，沿用 body pricing；沒有以可信套餐資料校驗 slug／價格。應由 server 查套餐或 CS draft 的權威價格，驗證場地、時間與加購。
### P1：KPay checkout 未驗登入／訂單擁有權／應付額
src/app/api/kpay/checkout/route.ts:64–118：直接用 body amount 建單，沒有 Firebase token 驗證；金額未由 booking 重算。webhook:248–265 接受成功付款後確認訂單，即使尚欠未清。風險包括任意金額付款、未達最低訂金仍確認、他人觸發付款單；不能單憑此點斷言尾數會被清零。應 server 計算應付額、驗擁有權與狀態，儲存 booking→payment order 對應及 idempotency key。
### P1：積分可自行改寫
firestore.rules:36–40 容許會員更新整個個人文件，包含 loyaltyPoints；bookings/create:207–215 又信任該餘額。應把積分改為伺服器專用欄位／ledger，會員僅可更改指定個人資料。
### P1：客戶文件存取過闊
firestore.rules:89–100 容許任何登入者 read booking_drafts（包括列出），claim 時未鎖定其餘欄位；storage.rules:33–36 容許任何登入者 read receipts。應分開 get/list、限制草稿 claim 欄位、入數紙按擁有者及授權員工存取。未讀取其他客戶文件作測試。
### P1：員工角色只在部分層面限制
firestore.rules 對 bookings、expenses、expense_templates、month_closes 等主要使用 isStaff，而 UI 的 cleaner／marketing／CS 權限更窄。例如 cleaner 在規則層也可寫財務資料。需建立同一份角色矩陣並落實於 server/rules；不能只隱藏頁面。
### P1：付款回調有中斷及併發窗口
webhook:212–224 先建立已處理 marker，再於 299 寫訂單；兩者並非同一 transaction。中途程序被終止後，重試會當作已處理。不同 transaction 同時完成亦可各自用舊 booking 計 balanceDue。另 311–313 明確會恢復已取消／過期訂單，只有 warning，可能與已重售時段衝突。建議付款記錄與餘額交易化、取消單付款轉人工處理、email／日曆等用可重試任務。
### P1：後台新增預訂 Hooks 次序
admin/bookings/new/page.tsx:183–200 在權限 early return 之後繼續 useMemo/useEffect/useState。lint 已確認違規；當權限狀態在渲染間改變可能出現 Hooks 數目錯誤。需將權限畫面與表單拆開或把 Hooks 移到所有 return 之前。
### P2：其他權限及環境問題
- blocked_slots 任意登入者可 create，存在惡意封鎖時段風險；應改為 server 管理。
- receipts 缺少檔案大小／MIME／擁有者路徑限制；多處規則缺乏欄位型別驗證。
- /api/email/welcome 接受任意 to，未驗登入或 rate limit，存在 email 濫用風險。
- 測試及正式共用 Firestore。lockPasscode.ts:193 只在 production 跳過 isTest；preview 本身沒有這道跳過條件。需核對 preview 有否真實 TTLock／email／收款憑證，不能當成完全隔離環境。
