# SPACO 網站架構檢討報告（2026-11-13）

寫俾 Heidi。用四個方向逐一讀晒代碼：① 新增分店會唔會自動跟上 ② 電子門鎖 ③ 各類設定項目嘅連動 ④ 預訂／付款／財務嘅 bug。報告以日常用語寫，技術位置（檔案名）放喺括號，方便之後開工。

標記：**[已核實]** = 我親自再睇過代碼確認；其餘係檢查人員讀代碼得出，未逐一再核。「(未核實)」= 未能睇到實際資料（我呢度連唔到資料庫同 Vercel）。

---

## 0. 一句總結

你嘅直覺係啱嘅。網站有**兩套世界**：一套係舊嘅「四間分店」寫死喺代碼入面（銅鑼灣、灣仔、尖沙咀、上環 A/B/全層），另一套係後來加嘅「分店管理」（資料庫）。大約三分之二嘅功能已經改咗睇分店管理，剩低三分之一仲係睇舊嗰套，所以每次加新嘢就有啲地方跟唔上。同樣道理，附加服務、套餐、來源渠道、按金扣款等「項目」大部分唔係數據，而係寫死喺代碼，有啲仲重複寫咗幾個地方，所以改一個地方其他地方唔會跟。

電子門鎖嘅問題係：設定分散喺兩個頁面加 Vercel 嘅環境變數，而且**冇任何畫面顯示佢係咪真係連接到**。

另外搵到幾個未發現嘅 bug，有三個會影響真實訂單／金錢，建議優先修。

## 1. 根本原因（點解會「加完又要再溝通」）

1. **分店有兩個來源。** 代碼入面有一份固定四間分店嘅清單（`src/lib/venues.ts`），分店管理嘅資料庫係後加嘅。好多舊功能仍然用固定清單搵分店（例如大部分電郵），所以 HART 呢類新分店喺嗰啲地方會變成「hart-a」呢種代號，或者直接唔出現。
2. **分店代號有三套。** 財務／獎金用一套（上環 = `sw`、HART = `tsthart`），公開網頁用另一套（上環 = `sheung-wan`），仲有高峰日、Google Calendar、內容管理各自一套。大部分情況啱得返，但有邊界位會出錯（見 §2.4）。
3. **「項目」唔係數據。** 附加服務嘅種類、套餐、行家／平台渠道、按金扣款項目、積分規則、按金級別，全部寫喺代碼。管理頁只可以改現有項目嘅價錢或者開關，**唔可以新增一個**；而且同一條規則有時寫咗四個地方（代碼、預訂須知、條款、FAQ），已經出現咗互相唔夾（例如預訂須知話 $20,000 以上訂單按金 $8,000，代碼最高只係 $4,000）。
4. **一條流程由幾個獨立掣砌成，中間冇同步。** 例如取消訂單、改狀態、記錄線下付款，各自係一個掣，各自做自己嗰步，冇一個「中央」確保時段、積分、優惠碼、Calendar 都一齊跟住變。

## 3. 電子門鎖（TTLock）

### 3.1 而家嘅實況

- **鎖 ID 可以喺兩個地方設**：分店管理每個房嘅「TTLock 門鎖 ID」，同埋 內容管理 → 系統設定 嘅 `ttlock_銅鑼灣／灣仔／上環A／B／全層／尖沙咀` 六個格。兩邊都有嘅話，**分店管理優先**。系統設定嗰六個格係舊嘢，而且只有舊六個場地，新分店冇格。
- **TTLock 帳戶登入只喺 Vercel 環境變數**（client id、secret、用戶名、密碼 MD5）。後台冇地方設、冇地方睇。
- **冇任何畫面顯示「連接成功／失敗」。** 預訂頁同 SOP 頁嗰個「TTLock／手動」標籤，只係睇系統設定有冇填數字，從來冇真係問過 TTLock；而且佢**唔睇分店管理嗰格**，所以只喺分店管理填咗鎖 ID 嘅分店（例如 HART）會被當成「手動」，staff 見到嘅係手動輸入表格，唔係「生成密碼」掣。
- 密碼點樣出：每日 09:00 自動掃未來三日已確認、已付清嘅訂單；付款確認、批核收據、改狀態為已確認時亦會即時試一次。密碼由開場前 1 小時有效到完場。
- 有六個「診斷」路由（scan／test／force／sweep）係一次性寫嘅，後台冇掣用，要用 CRON_SECRET 先開到，staff 用唔到。

### 3.2 門鎖嘅問題（按嚴重性）

**高**
1. 取消訂單時，如果刪除 TTLock 密碼失敗，系統只係靜靜記 log，但照樣將訂單上嘅密碼清走。**門鎖上嘅密碼仍然有效**，冇人會知，亦冇得重試。(`lockPasscode.ts` 約 458-472)
2. 密碼生成咗但電郵發送失敗，之後永遠唔會再試（因為「已有密碼」），畫面亦冇顯示電郵未發。另外如果 Email 自動化嗰個「門鎖密碼」開關熄咗，記錄仍然會寫「已發送」。
3. 新分店喺預訂頁被當成手動（見上）。
4. 每日自動掃嘅失敗（冇鎖 ID、生成失敗）冇人會收到通知。

**中**
5. 提早入場：客人買咗 2 小時提早佈置，密碼仍然只係開場前 1 小時先生效。
6. 訂單改時間後，已生成嘅密碼有效時間唔會跟住改。
7. 分店管理入面**清空鎖 ID 係清唔走嘅**（空白會被忽略，舊值保留）。
8. OAuth 回調頁冇登入保護，會將長期有效嘅 refresh token 直接顯示喺網頁。
9. 自動化開關嘅說明文字寫「每日 01:00／03:00」，實際係 09:00。

### 3.3 建議：一個「門鎖設定」頁取代所有散落嘅設定

放喺 系統管理，只限 Admin：

1. **帳戶連接卡**：顯示環境變數有冇設（只顯示名，唔顯示值）、用緊邊種登入方式、token 有效期、最後一次成功呼叫時間；一個「**測試連線**」掣（取 token → 列出帳戶內所有鎖），結果用中文顯示。
2. **每間分店／每個房一行**（由分店管理自動列出）：鎖 ID 用下拉選（直接由 TTLock 帳戶列出，顯示名稱、電量）、確認鍵（# 或 🔔）、門鎖指引圖、模式（自動／手動）、狀態燈（有 ID／鎖喺帳戶入面／電量／有冇 gateway）、「**測試此門鎖**」掣（加一個 10 分鐘密碼再即刻刪，唔顯示數字）。
3. **規則**（唯讀）：開場前 48 小時開始生成、開場前 60 分鐘（或提早入場時間）生效、要付清尾數、每日 09:00 掃。
4. **最近活動**：最後一次自動掃嘅時間同結果（生成／提醒／跳過／失敗數目）、未來三日未有密碼嘅訂單同原因、電郵未發嘅、刪除失敗嘅，每項有重試／刪除／重發掣。
5. **搬遷**：將系統設定嘅 `ttlock_*`、`lockguide_*` 搬入分店管理，刪走舊格；預訂頁同 SOP 頁改為讀同一個來源；刪走六個診斷路由同無保護嘅 OAuth 頁。

## 5. Bug 清單

### 高（影響真實訂單／金錢／安全）

1. **[已核實] 後台「直接落單」如果當時未記錄任何付款，15 分鐘內會被自動取消。** 直接落單冇付款時狀態係「待付款」但冇設到期時間；自動清理每 15 分鐘跑一次，冇到期時間會當已過期 → 改成「未完成付款」、釋放時段、刪 Google Calendar 事件。行家「之後先付」嘅單會中招。(`booking-direct/route.ts:211`、`expire-pending-bookings/route.ts:64`)
2. **[已核實] 直接落單唔會檢查 HART 其他房。** 撞期清單係上環寫死嘅；HART 只喺分店管理，所以 A+B 全場落單唔會睇 Room A／B 嘅單。客人訂咗 Room A，CS 再落一張同日全場，冇任何提示。(`booking-direct/route.ts:13-21,105`)
3. **[已核實] Google Calendar 連接可以俾任何人接管。** `/api/google/callback` 冇登入檢查、冇核對 state，任何人跑一次授權流程就會覆蓋你嘅 token。之後同步失效 → 部份 Calendar 手動記錄唔再擋時段，而且所有待處理嘅付款後續工作會每 5 分鐘重發電郵（見 #8）。
4. **手動改狀態唔會處理時段。** 將已過期／已取消嘅單改返「已確認」，時段唔會重新鎖（網站照賣）；改做「未完成付款」，時段又唔會放。
5. **補記錄過期單嘅付款時，時段重建冇撞期檢查。** FPS 單過咗期、時段已賣俾另一個客，之後 staff 補記錄 FPS → 兩張單都已確認、時段重疊，冇提示。
6. **[已核實] 積分同優惠碼只喺兩條確認路徑會扣。** 「已於線下付款」、後續付款、結算尾數、改狀態呢幾條路都**唔會扣積分、唔會計優惠碼使用次數**。另外付款確認路由如果客人冇電郵，會喺扣積分之前就返回。即係 FPS 客用咗積分同單次現金券，經線下付款確認後，積分仍在、現金券可以再用。
7. **[已核實] 記錄退款會令客人變成欠款人。** 退款係以負數付款記錄，但單據總額不變 → 尾數變正數 → 客人被鎖唔可以再訂、收到第 14／30 日欠款提醒。例如已完成嘅單補償 $300 俾客，客人就「欠」$300。
8. **付款後續工作會無限重試並每次重發晒電郵。** 任何一步失敗（例如 Google token 失效）就整個失敗，每 5 分鐘再做一次：確認電郵、staff 電郵、供應商落單電郵全部重發，供應商可能送兩次。
9. **[已核實] 任何人可以讀到 Google Calendar 事件嘅標題同內容。** `blocked_slots` 公開可讀，而同步會將 Calendar 事件標題／描述（通常有客人名、電話）存入去。

### 中

10. 客人可以自己解除欠款封鎖、無限期霸住時段：規則容許單主將「已確認」改成「待審核」，只要填一個任意字串做收據網址，唔需要真係上載檔案。
11. 幾個冇登入保護嘅路由：`google/push-booking`（任何人可以刪 Calendar 事件或者塞文字）、`email/booking-cancelled`（會向未取消嘅單發「已取消」電郵）、`email/offline-pending`、`notify-receipt-pending`、`email/welcome`、`translate`（免費用你嘅 AI 額度）。
12. 取消訂單唔會退積分、唔會回復優惠碼次數（退積分嘅函數寫咗但冇地方用）。
13. 取消同改狀態喺瀏覽器逐步寫，中途關 tab 會變成「已取消但時段仍鎖住」或者相反。
14. 測試訂單修改後，時段唔會標記為測試，會喺正式站擋真客（到 10:30 清理先消失）。
15. 伺服器唔會檢查新訂單自己嘅 60 分鐘清潔時間（網頁會檢查，但 CS 連結或者客人延長完場時間可以撞到下一張單前 30 分鐘）。
16. 客人自行修改訂單冇驗證時間格式、冇訂單層面嘅重疊檢查；亂嘅時間會令小時數同價錢變成 NaN 寫入資料庫。
17. Google Calendar 鏡射：跨午夜嘅事件只擋到 23:59；多日全日事件只擋第一日。
18. 編輯已取消／已過期嘅單會重建時段；已驗證付款但已取消嘅單可能被重新推上 Calendar；測試單可能推上真 Calendar。(推斷，未完全核實)
19. 會員管理嘅「調整積分」掣**永遠失敗而且冇提示**（用咗冇權限嘅寫法；其實已有正確 API 可以用）。
20. `scan-status-repair?apply=1` 呢個一次性修復路由會將所有待審核但仍欠款嘅單變成已確認，包括 KPay 需要人手審核嘅單。建議刪。

### 低

21. 按金結算時，超出按金嘅欠款部分會即時俾積分（應該收到錢先俾），而且雙擊會俾兩次。
22. 優惠碼日期用 UTC：凌晨 0 至 8 時，昨日到期嘅碼仍然有效、今日生效嘅碼未生效。
23. 財務總覽冇扣 staff 折扣（月結有）；行家佣金嘅場租基礎冇扣場租折扣。
24. 五個定時路由如果 `CRON_SECRET` 未設會變成無保護；門鎖密碼路由接受 `?key=` 參數（會留喺 log）。
25. 活動後電郵只針對「剛好三日前」嘅單，漏跑一次就永遠唔補；唔會跳過測試單；開關熄咗仍標記已發。獎金嘅營業額用優惠碼前嘅毛額，同月結唔一致。

27. 後台有約 20 個一次性「診斷／修復」路由，冇 UI 用，其中 8 個會改資料（有一個 GET 就會真係發門鎖密碼同電郵）。建議刪走或者加確認。

## 6. 建議路線圖

### 第一階段：止血（修 bug，1–2 日）
- #1 直接落單被自動取消 · #2 直接落單撞期 · #3 Google 授權保護 · #6 積分／優惠碼統一扣 · #7 退款唔當欠款 · #9 Calendar 內容唔公開 · #11 路由加保護 · #19 調整積分掣 · #20 刪危險路由。

### 第二階段：一個分店來源（3–5 日）
- 所有電郵、客人頁面（成功頁、我的預訂、修改）、預訂管理列表、SEO／sitemap／JSON-LD／llms.txt、Google Calendar 標題、Excel 場地代碼，全部改讀分店管理。
- 分店管理加欄位：首頁大圖、門鎖指引圖、確認鍵、地區、座標；新分店自動有利潤分配提示。
- 刪走代碼入面嘅固定四間分店清單（只留作緊急後備）。
- 財務代號：以分店管理嘅 branchKey 做唯一代號，舊代號用對照表。

### 第三階段：門鎖設定頁（2–3 日）
- 按 §3.3 做一頁，加取消時刪密碼失敗嘅重試同提示、電郵未發嘅重試、提早入場時間、改時間後更新密碼。

### 第四階段：項目變數據（分批，每批 2–4 日）
1. 附加服務：每個附加服務一筆資料（類別＝財務分欄、要唔要通知供應商、單位、staff 標籤、表格款式），預訂頁、供應商電郵、財務、Calendar、收據全部讀同一筆。可以新增附加服務。
2. 來源渠道：一個渠道清單（含平台渠道、佣金、係咪客人可見、Excel 要唔要獨立欄）。
3. 套餐：搬入資料庫，有管理頁，可以綁多間分店。
4. 按金扣款項目、按金級別、積分規則：一個設定文件，預訂須知／條款／FAQ 由佢生成。
5. 首頁篩選改讀分店管理；高峰日「全場優先」改用房間關係。

### 第五階段：流程中央化（2–3 日）
- 取消、改狀態、記錄付款、修改時間，全部經伺服器一個交易完成：時段、積分、優惠碼、Calendar、門鎖一齊處理，失敗就整個唔做。
- 付款後續工作每步記錄完成，有上限，失敗通知 staff。

每階段都會先上測試站俾你試。
